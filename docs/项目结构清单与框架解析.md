# 智能个人助理系统 · 项目结构清单与框架解析

> 面向初学者。本文做四件事：
> 1. 逐文件说明每个文件的作用、属于哪个模块；
> 2. 重点剖析 `backend/` 与 `frontend/src/` 的代码分工；
> 3. 用大白话讲清 **LangChain / LangGraph 是怎么搭起来的**，以及 **RAG 知识库**的运行链路；

## 一、整体架构（一句话版）

```
浏览器(React)
   │  HTTP/JSON + SSE(流式)
   ▼
FastAPI  ──▶  LangGraph Agent（大模型 + 工具循环）
   │                 │
   │                 ├─▶ tools.py       计算 / 天气 / 搜索 / 待办 / 通知
   │                 └─▶ rag.py         知识库检索（向量余弦）
   ├─▶ SQLAlchemy ──▶ SQLite(app.db)
   └─▶ Ollama / 云端 OpenAI 兼容 API
```

- **前端**负责：界面、登录态、把消息发到后端、把回复"打字机"式渲染出来、模型/技能/知识库的勾选。
- **后端**负责：校验身份(JWT)、存消息、调用大模型、把工具结果拼回对话、知识库的切分与向量化。
- **AI 层**（`agent_manager.py` + `tools.py` + `rag.py` + `chat.py`）负责：把"大模型"和"工具/知识库"组装成一个会思考、会调工具、会翻资料回答的智能体。

### 3.3 数据层（12 张表 · 初学者版）

- **`User`**：一个账号。`username`、`hashed_password`、`nickname`、`avatar`、`language`、`font_size`、`theme`。
- **`Conversation`**（会话）：一次连续聊天。`user_id`、`title`、`provider`/`model`（本会话用哪个模型）、`active_skill_ids`（启用的技能）、`active_kb_ids`（参与检索的知识库）。
- **`Message`**（消息）：`conversation_id`、`role`(`user`/`assistant`)、`content`、`ref_file_ids`（本条引用的附件）、**`provider`/`model`（本条回答由哪个模型生成）**。
- **`TodoItem`**：待办事项。
- **`Skill`**：技能（`name` / `description` / `prompt` / `is_enabled`）。
- **`FileItem`**：上传的文件（`filename` / `stored_path` / `size` / `content` 抽取的正文 / `collection_id` 所属知识库）。
- **`Notification`**：站内通知（铃铛）。
- **`KbCollection`**：知识库（一个"知识集合"）。
- **`KbChunk`**：知识片段（`file_id` / `collection_id` / `chunk_index` / `text` / `embedding` 向量 JSON）。
- **`Note`**：智能笔记（`user_id` / `day`（YYYY-MM-DD）/ `title` / `content` Markdown 正文）。
- **`Schedule`**：日程（`user_id` / `title` / `start_at` **epoch 秒** / `note` / `notified` 是否已提醒过）。
- **`Course`**：课程（`user_id` / `name` / `weekday` / `start_section` / `end_section` / `teacher` / `location` / `weeks` 周次表达式 / `color`）。

**多用户隔离的根**：几乎所有查询都带 `user_id` 过滤（例如 `chat.py` 先查 `Conversation` 再校验 `user_id == current_user.id`），否则会越权看到别人的数据。

## 五、★ LangChain / LangGraph 是怎么搭起来的

### 5.1 三个关键概念

1. **LLM（大模型）= 大脑**：接收消息列表、吐出回复。`build_llm()` 里构建，支持本地 Ollama 或云端 OpenAI 兼容。
2. **Tool（工具）= 手脚**：计算器、查天气、记待办、**查知识库**……模型自己不会算数 / 联网 / 翻资料，但能"决定调用工具"。用 `@tool` 装饰普通函数即可（见 `tools.py`）。
3. **Agent（智能体）= 大脑 + 手脚的自动循环**：LangGraph 的 `create_react_agent` 把两者捆在一起，自动循环：
   **想 → 调工具 → 看结果 → 再想 → 回答**。

### 5.2 一条消息的完整旅程（看 `chat.py`）

```
用户发消息
  │
  ▼
/api/chat 或 /api/chat/stream
  ├─ _prepare_conversation()   写用户消息（regenerate 则先删掉旧回答）
  ├─ _attachment_context()     把引用附件的正文拼到问题前
  ├─ _image_blocks()           把图片附件转成多模态消息块（交给视觉模型）
  │
  ▼
get_agent_for_conversation()          ← agent_manager.py
  ├─ 命中 agent_cache 就直接复用
  ├─ 否则 build_llm() 建大脑 + 组装工具 + 拼技能指令 → _create_agent()
  └─ 缓存键 = (会话, 模型, 技能, 知识库)
  │
  ▼
agent.invoke(...) / agent.stream(...)
  ├─ thread_id = 会话 id → LangGraph 用共享 MemorySaver 记住这个会话的历史
  ├─ 内部循环：模型看消息 → 需要就调工具 → 结果回填 → 继续 → 最终回答
  │
  ▼
回写 assistant 消息（含 provider / model）→ 返回前端（流式版用 SSE 逐字推）
```

| 思考过程怎么从正文里剥出来 | `chat.py` → `_ThinkSplitter` |
| 图片怎么交给模型 | `chat.py` → `_image_blocks()` |

### 5.4 记忆为什么"接得上"（最容易懵的点）

LangGraph 的 `MemorySaver` 保存某个 `thread_id` 下的完整消息状态。我们在 `chat.py` 里写死：

```python
config = {"configurable": {"thread_id": str(conv.id)}}
```

**用"会话 id"当记忆身份证**。于是：

- 同一会话多轮提问 → 同一个 `thread_id` → 记忆共享 → 模型记得你前面说了啥；
- 不同会话 → 不同 `thread_id` → 记忆互不干扰；
- 关键改进：`MemorySaver` 在 `agent_manager.py` 里是**全局共享的一个实例**，
  所以**切换模型 / 技能 / 知识库导致 Agent 重建时，历史不会丢**（早期"每个 Agent 各建一份记忆"会导致一换模型就失忆）。

### 5.5 工具为什么"安全"且"多用户隔离"

- **计算器不用 `eval`**：`tools.py` 用 `ast` 白名单解析，只认 `+ - * / ** % //` 和正负号，杜绝任意代码执行。
- **待办 / 通知 / 知识库按用户隔离**：`make_todo_tools(user_id)` 这类"工厂函数"先捕获当前 `user_id`，
  返回的工具内部自动用该 `user_id` 落库 / 检索。模型只传业务参数，不知道也不关心"这是谁的"。

## 六、★ RAG 知识库是怎么跑起来的

### 6.1 入库（上传时）

```
上传文件 → files.py 抽取正文(content)      ← 解析放 run_in_threadpool，不阻塞事件循环
  ├─ 图片：不抽正文，交给多模态模型直接看
  ├─ PDF ：pypdf 逐页抽取文字
  ├─ Word：标准库 zipfile + ElementTree 读 word/document.xml（.docx 本质是 zip + XML，零新增依赖）
  └─ 文本：截断到 50 万字符上限后 → rag.index_file()
        ├─ split_text()  按段落/句号优先切分，500 字/段、80 字重叠
        └─ embed_texts() 调本地 Ollama /api/embed（bge-m3）**分批**算向量
              └─ 逐批写入 kb_chunks 表（text + embedding）
```

### 6.2 检索（提问时）

```
Agent 决定调用「知识库检索」工具 → tools.make_kb_tools()
  └─ rag.search(user_id, query, collection_ids)
        ├─ 把 query 向量化（一次）
        ├─ 取出该用户（或选中知识库）的全部片段
        ├─ 按 collection_id 分组，各自算余弦相似度
        └─ **每个知识库各取自己配置的 Top-K**（NULL 则跟随全局默认 4）→ 合并排序
              ├─ 总上限 RAG_MAX_TOTAL_CHUNKS（默认 30）防止多库时撑爆上下文
              └─ 工具结果以「【文件名】正文」格式拼装
                    └─ chat.py 用 _extract_sources() 正则抽出文件名 → 推给前端做「来源」标注
```

### 6.3 容量与性能

| 项 | 现状 |
|---|---|
| 单文档字数 | ≤ **50 万字符**（`MAX_CONTENT_CHARS`，超出会被静默截断） |
| 单文件大小 | ≤ **50 MB**（`MAX_UPLOAD_MB`） |
| 单库文档数 | **无硬性上限**，受检索性能约束（几十~几百篇体验良好） |
| 向量化 | **分批**（`RAG_EMBED_BATCH` 默认 32）：长文档可切上千段，一次 POST 必然超时 |
| Top-K | **按知识库生效**（`kb_collections.top_k`，NULL 跟随全局 `RAG_TOP_K`）；规范库建议 2~3、资料库 8~10 |
| 超长文本 | 可整本上传（上限 50 万字符）；仍嫌不够时按章节分卷导入 |
| 向量化速度 | 本地 CPU 约 1~3 段/秒；**不消耗云端额度**（本地 Ollama 免费） |

## 七、其他值得知道的设计

- **模型切换与标注**：`ModelPicker` → `PATCH /api/sessions/{id}` 写库；回答保存时把 `provider/model` 落到 `messages` 表，
  因此**刷新后仍能看到"这段是哪个模型答的"**。
- **思考过程**：推理模型（或本地 `OLLAMA_THINK=true`）的思考内容，后端用 `_ThinkSplitter` 从流式正文里剥离（能处理标签跨数据块），
  以独立事件推给前端，在回答上方折叠展示，**不混进正文**。
- **附件问答**：`file_ids` 只影响"这一问"，不落库到消息正文，避免污染历史。
- **主题 / 字号 / 语言**：存在 `users` 表，登录后由服务端偏好覆盖本地 `localStorage`。
