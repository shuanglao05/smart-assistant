## 一、30 秒电梯陈述

> **IPAS 是一个可私有化部署的多用户智能个人助理。**
> 它把大模型接进了真实的工作流：支持本地 Ollama 与多家云端 API 自由切换，
> 内置一个带工具调用能力的 ReAct Agent（能算数、查天气、记待办、发通知、翻知识库），
> 一套零新增依赖的 RAG 知识库（PDF/Word/文本自动切分向量化），
> 以及会话、技能、日程、课表、笔记、计时器等完整功能模块。
> 前后端分离，React + TypeScript + Vite / FastAPI + SQLAlchemy + SQLite，
> 全链路 SSE 流式输出，首字延迟从 42 秒优化到 1 秒。

**如果只能说一句**：
> 「我做了一个能调工具、能翻自己资料的 AI 助理，重点解决了**大模型工程化落地时的性能、稳定性和多用户隔离**问题。」

### 2.2 三个"反直觉"的选型（面试官最爱追问）

**① 为什么不用 Chroma / FAISS / Milvus，而是用 SQLite 存向量？**

> 因为**数据规模决定了这是过度设计**。我的实测判据是：
> - 0 ~ 5 万片：SQLite 存 JSON 向量 + 纯 Python 余弦（暴力精确检索，毫秒级）——**我的项目 3445 片，正处此档**
> - 5 万 ~ 50 万片：SQLite + FAISS
> - 50 万片以上或需多租户水平扩展：才上 Chroma / Milvus
>
> 更关键的一点：**RAG 检索的真正瓶颈不在向量库，而在调 Ollama 生成 query 向量的那次网络往返**。
> 换向量库省不掉这个开销，属于"优化了不痛的地方"。
> 我在架构上做了隔离——`rag.py` 里的 `index_file()` 和 `search()` 是唯二需要改的函数，
> 上层（工具、Agent、API）完全不用动，所以将来要换成本是可控的。

**② 为什么 .docx 解析用标准库而不用 python-docx？**

> docx 本质是 **zip 包 + WordprocessingML**。我用 `zipfile` 读出 `word/document.xml`，
> 再用 `ElementTree` 遍历 `{ns}p`（段落）和 `{ns}t`（文本节点）就拿到了全部正文，
> 连表格单元格里的段落也一并遍历到。**约 20 行代码，零新增依赖**。
> 少一个依赖就少一个版本冲突的可能——这个项目里我已经因为 passlib 踩过一次坑（见 7.2）。

**③ 为什么密码哈希直接用 bcrypt 而不用 passlib？**

> 因为 **passlib 1.7.4 在 Python 3.13 + bcrypt 4.x 下会抛
> `AttributeError: module 'bcrypt' has no attribute '__about__'`**。
> passlib 已长期不维护，与其等它修，不如直接用底层 bcrypt——
> 我额外处理了一个细节：**bcrypt 只取前 72 字节**，超长密码会抛 ValueError，所以我先做截断。

### 3.4 多用户隔离设计（安全核心）

**根原则：几乎所有表都带 `user_id` 外键，任何查询都必须带上 user_id 过滤。**

三层隔离：

1. **接口层**：`get_current_user` 从 JWT 解出 user_id，所有查询强制
   `.filter(XxxModel.user_id == current_user.id)`——查不到就 404，不泄露"存在但无权"。
2. **工具层**：用**工厂函数 + 闭包**把 user_id 绑进工具（见 4.3）。
3. **数据层**：文件按 `data/uploads/u{user_id}/` 分目录；知识库片段靠
   `user_id + collection_id` 双重过滤。

> ⚠️ 我踩过的坑：排查"知识库数据不见了"时，第一反应应该是**先查 user_id 归属**，
> 而不是怀疑前端过滤或数据丢失。这个项目里我两次遇到"看起来不对、实际没问题"的情况
> （一次是 user_id，一次是 WAL 未 checkpoint 导致外部工具读到旧快照）。

## 四、Agent 如何调工具（ReAct 全链路）

### 4.1 什么是 ReAct

**ReAct = Reasoning（推理）+ Acting（行动）**。核心是一个循环：

```
① 模型看当前消息 → 决定「直接回答」还是「先调工具」
② 若调工具 → 执行工具 → 把结果作为 ToolMessage 放回消息列表
③ 回到 ①，模型带着工具结果再想 → 直到给出最终回答
```

我用的是 LangGraph 的 `create_react_agent`，**这个循环不用自己写**——
只要把「模型 + 工具 + 系统提示词 + 记忆」交给它。

```python
create_react_agent(llm, tools, prompt=system_prompt, checkpointer=_CHECKPOINTER)
```

### 4.2 工具是怎么让模型"看懂"的

关键在 **`@tool` 装饰器 + docstring**：

```python
@tool
def calculator(expression: str) -> str:
    """计算数学表达式。输入一个算术表达式字符串，例如 '2+3*4'，返回计算结果。"""
```

`@tool` 会把 **函数名 + 参数类型注解 + docstring** 自动转成 JSON Schema，
随请求发给模型（OpenAI 兼容协议里的 `tools` 字段）。
模型据此判断"什么时候该调、传什么参数"，然后返回一个 `tool_calls` 结构，
LangGraph 解析后真正执行 Python 函数。

> **面试要点**：docstring 就是**给模型看的说明书**，不是给人看的注释。
> 写不清用途和输入格式，模型会误用或干脆不用工具。
> 我的写法是固定格式：**「做什么。输入什么（含示例），返回什么。」**

### 4.3 工具清单与"工厂函数"设计（最能体现工程思考）

**全局工具（4 个，单例）**：

| 工具 | 作用 | 实现要点 |
|---|---|---|
| `calculator` | 算数学表达式 | **AST 白名单解析，绝不用 eval**（见下方安全说明） |
| `get_weather` | 实时天气 | 高德优先，未配 Key 回退 OpenWeatherMap |
| `get_weather_forecast` | 未来 1~4 天预报 | 高德 `extensions=all`，白天/夜间粒度 |
| `search_web` | 网页搜索 | duckduckgo，**未安装时优雅降级返回提示**而非崩溃 |

**用户隔离工具（工厂函数生成）**：

```python
def make_todo_tools(user_id: int):
    @tool
    def add_todo(task: str) -> str:
        """添加一条待办事项。输入待办内容文本，返回添加成功提示。"""
        db = SessionLocal()
        try:
            todo = TodoItem(user_id=user_id, task=task)  # ← 闭包里的 user_id
            db.add(todo); db.commit()
            return f"已添加待办：{todo.id} - {todo.task}"
        finally:
            db.close()
    return [add_todo, list_todos]
```

**为什么必须用工厂函数而不是普通 `@tool`？**（面试高频）

> 因为工具内部要写数据库，写库就必须知道"这是哪个用户的数据"。
> 两种坏方案：
> - 把 `user_id` 作为工具参数暴露给模型 → **既不安全（模型可伪造别人的 id）也别扭**
> - 用全局变量存当前用户 → **并发请求会串号**
>
> 我的方案是**闭包**：外层 `make_todo_tools(user_id)` 先捕获住 user_id，
> 返回已绑定该用户的工具。模型调用时只传 `task`，工具内部自动用闭包里的 user_id 落库，
> **天然实现多用户隔离，且模型无法越权**。

同理还有 `make_notification_tools(user_id)` 和 `make_kb_tools(user_id, kb_ids)`——
后者连"本次对话启用了哪些知识库"也一起绑进去了。

### 4.4 安全计算器的 AST 白名单（安全必答）

**绝不用 `eval`** —— `eval("__import__('os').system('rm -rf /')")` 能执行任意代码。

我的做法是把表达式解析成 AST，**只允许白名单节点**：

```python
_ALLOWED_BINOPS = {ast.Add: operator.add, ast.Sub: operator.sub,
                   ast.Mult: operator.mul, ast.Div: operator.truediv,
                   ast.Pow: operator.pow, ast.Mod: operator.mod,
                   ast.FloorDiv: operator.floordiv}
_ALLOWED_UNARY = {ast.USub: operator.neg, ast.UAdd: operator.pos}

def _safe_eval(node):
    if isinstance(node, ast.Expression): return _safe_eval(node.body)
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _ALLOWED_BINOPS:
        return _ALLOWED_BINOPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _ALLOWED_UNARY:
        return _ALLOWED_UNARY[node.op](_safe_eval(node.operand))
    raise ValueError("不支持的表达式")   # ← 函数调用、属性访问、下标全部拒绝
```

任何 `ast.Call`（函数调用）、`ast.Attribute`（属性访问）、`ast.Name`（变量名）都会走到
最后的 `raise`——**从根本上杜绝代码注入**。

### 4.5 Agent 缓存机制（性能必答）

**问题**：每次提问都重建 Agent 要初始化大模型、绑定工具，开销不小。

**方案**：进程级字典缓存，**缓存键是 8 元组**：

```python
cache_key = (
    conversation_id,      # 会话
    provider,             # ollama / cloud
    model,                # 具体模型名
    active_ids_sorted,    # 启用的技能 id（排序后的元组）
    active_kb_ids,        # 启用的知识库 id
    thinking_flag,        # 深度思考开关
    budget,               # 思考预算
    pvid,                 # provider_id（多 API 接入）
)
```

> **为什么要 8 个维度？** 因为**任何一个配置变了，Agent 都必须重建，否则新配置不生效**。
> 我踩过这个坑：思考开关没进缓存键时，用户在设置里打开"深度思考"，
> 但旧 Agent 还在用旧配置，界面显示开了、实际没开。
>
> 另一个坑：切换会话模型时，`payload.model` 必须**优先于** provider 的默认模型。
> 我曾写成 `conv.model = prow.model`，导致"只能切到各 provider 的默认模型"，
> 同一 provider 下的其他模型永远选不上。

**内存泄漏防护**：删除会话时调 `evict_agent()`，遍历缓存键、把该会话的所有变体
（不同模型/技能组合）全部清掉。

### 4.6 记忆设计（最容易被问倒的点）

**关键决策：全局共享一个 `SqliteSaver`，所有 Agent 共用同一份记忆，按 `thread_id` 隔离。**

```python
_CHECKPOINT_DB = config.DATA_DIR / "checkpoints.db"
_ckpt_conn = sqlite3.connect(str(_CHECKPOINT_DB), check_same_thread=False)
_CHECKPOINTER = SqliteSaver(_ckpt_conn)
```

**为什么不用 MemorySaver（内存版）？**

> 早期我就是用 MemorySaver，结果出现一个诡异的矛盾：
> **界面上明明还看得到昨晚的聊天记录，AI 却说"我看不到之前的对话"**。
> 原因是：界面历史来自 `messages` 表（SQLite，持久），
> 而 AI 的上下文来自 MemorySaver（内存，**后端一重启就全没了**）。
> 换成 SqliteSaver 后，记忆写进 `checkpoints.db`，重启也能接上。

**为什么全局共享而不是每个 Agent 一份？**

> 因为切换模型/技能/知识库会导致 Agent 重建。
> **如果每个 Agent 各建一份记忆，一换模型就会"失忆"**——用户切个模型，前面聊的全忘了。
> 共享同一个 checkpointer 后，记忆按 `thread_id`（= 会话 id）天然隔离，
> 不同会话互不干扰，同一会话换模型也能接上历史。

**为什么 `check_same_thread=False` 是必须的？**

> FastAPI 用线程池处理请求，同一个 SQLite 连接会被不同线程使用。
> SQLite 默认禁止跨线程使用连接，会抛错。
> 关掉这个检查是安全的——**SqliteSaver 内部有锁保证并发安全**。

## 五、RAG 全链路与向量检索

### 5.1 入库链路（Indexing）

```
用户上传文件
  ↓ ① 校验类型（PDF/docx/文本代码/图片）+ 大小预判（≤50MB）
  ↓ ② 落盘 data/uploads/u{user_id}/{uuid}{ext}
  ↓ ③ run_in_threadpool 解析正文 ← 关键：必须离开事件循环
  │    ├─ PDF：pypdf 抽字 → _clean_pdf_text 版式清洗
  │    ├─ docx：zipfile 读 word/document.xml → ElementTree 遍历 w:p / w:t
  │    ├─ 文本/代码：decode utf-8（去 BOM），失败回退 latin-1
  │    └─ 图片：不抽正文，留给多模态模型直接看
  ↓ ④ 截断到 MAX_CONTENT_CHARS（50 万字符，防爆上下文）
  ↓ ⑤ 写 files 表（含抽取的 content，供聊天直接注入）
  ↓ ⑥ run_in_threadpool → rag.index_file()
  │    ├─ 删该文件旧片段（可重复执行，幂等）
  │    ├─ split_text() 语义感知切分 → N 个片段
  │    ├─ embed_texts() 分批向量化（批大小 32）
  │    └─ 逐条写 kb_chunks（text + json.dumps(vector)）
  ↓ 返回片段数
```

### 5.2 语义感知切分算法（**技术含量最高的一块，重点准备**）

**旧实现的问题**：定长 500 字符窗口 + 窗口内找断点。当断点落在窗口前半段时，
直接在第 500 字符处硬切；下一段起点回退 overlap 时不校正边界。
结果**实测 3100 片里有 322 片以逗号或引号开头**——上一句话被腰斩了。

**新实现：三段式**

```python
① _split_units(text) → [(单元文本, 是否小标题)]
   空行分段 → 换行分行 → 小标题单独成单元 → 其余按句切分
   ↓ 保证：任何单元内部都是完整句子

② 贪心合并单元
   while j < n and length + len(units[j][0]) <= size:  # size=500
       buf.append(units[j][0])
   ↓ 单个单元超长时 _split_long_unit() 按逗号二次切分

③ 重叠 = 回退若干【完整单元】
   while back > i+1 and acc + len(units[back-1][0]) <= overlap:  # overlap=80
       back -= 1
   ↓ 保证：重叠区域也是完整句子，不是固定 80 字符的硬切
```

**结果**：片段收尾是完整句，开头也是完整句，检索语义干净得多。

#### 三个血泪细节（说出来就是加分项）

**① 中文 `…` 和 `——` 绝不能当句末符**

```python
_SENT_END = "。！？!?；;"     # ← 句末符只有这些
_DANGLING = "…—～-·"          # ← 仅"整行只剩停顿符号"时才算收尾
```

> 小说语料里 `"怎么好像…地狱列车一样？"` 这种句中停顿极常见。
> 把 `…` 当句末符会产出**以 `…` 开头的碎片**（实测 350 片里有 14 片）。
> 处理办法：`_split_units` 里判断"整行 strip 掉停顿符号后为空"，
> 就把它**贴回上一单元**，不让它独立成片。

**② 小标题判定必须限长**

```python
def _is_heading(line: str) -> bool:
    s = line.strip()
    return bool(s) and len(s) <= 40 and bool(_HEADING_RE.match(s))
```

> 正则匹配 `第X章 / 第X条 / 一、 / 1.1 / （一） / 附录A / #标题`。
> 但**不限长会出大问题**：`第一条 为了维护……`（这是条文正文，不是标题）
> 会命中 `第一条` 特征被误判为标题，反而把句子截断。
> 所以我加了 `len <= 40` 的硬限制。

**③ 句边界要吞掉后引号**

```python
_SENT_TAIL = "\u201d\u2019\u300d\u300f\uff09)】]》…"   # " ' 」 』 ） ) 】 ] 》
```

> `他说"好。"` 的句边界应该在**后引号之后**，不是引号之前。
> 所以我**逐字符扫描**而非用正则切分，遇到句末符后继续吞掉紧跟的收尾符号。

### 5.3 PDF 版式清洗（`_clean_pdf_text`，仅对 PDF 做）

**为什么必须清洗**：pypdf 按**页面视觉排版**抽字，一行到纸张右边缘就换行，
一句话常被拆成两三行。连锁问题：① 分片器优先命中这些"假换行"，把句子切碎；
② 段落结构丢失，检索出的片段看不出上下文关系。

**清洗规则**（中英文判定相反，这是实测出来的）：

| 步骤 | 规则 |
|---|---|
| 预处理 | 统一换行符、全角空格转半角 |
| 去噪 | 剔除 `第 N 页` / `- N -` / `Page N of M` 页眉页脚 |
| ① 英文断词 | 行尾 `-` 且下一行以小写字母开头 → 去连字符直接接（`transla-` + `tion` → `translation`） |
| ② 短标题独立 | 上一行或本行像标题（≤30 字）→ 断段 |
| ③ 明显未结束 | 上一行以 `，、：（【《"'；—` 收尾 → 同一段 |
| ④ 明显已结束 | 上一行以 `。！？…"』）】》.` 收尾 → 断段 |
| ⑤ 其余 | **接回同一段**（中文行末无标点 = 版式换行；英文行末无标点 = word wrap） |

拼接时 `_join_lines` 还要判断：**英文/数字之间补空格，中文与中文直接相接**。

> ⚠️ 关键边界：**txt 和 docx 的换行本来就是语义换行，绝对不能清洗**。
> 我只对 PDF 走这条路径。

### 5.4 向量化（Embedding）

```python
def _embed_batch(texts):
    """优先新版 /api/embed（一次传多条），失败回退旧版 /api/embeddings 逐条"""
    resp = requests.post(_EMBED_URL, json={"model": "bge-m3", "input": texts}, timeout=120)
    ...

def embed_texts(texts, batch_size=None):
    bs = max(1, batch_size or config.RAG_EMBED_BATCH)   # 默认 32
    for i in range(0, len(texts), bs):
        out.extend(_embed_batch(texts[i : i + bs]))
```

**为什么必须分批**（面试必答）：
> 长文档能切出上千个片段，**一次性 POST 给 Ollama 极易超时**（120s 也扛不住）。
> 分批后每批独立完成，既稳又快，**也不会因一批失败丢掉全部结果**。

**本机实测吞吐**（说出来证明你真跑过）：
- 批量 32 条（约 480 字/条）：**约 21 秒**
- 单条：**约 15 秒**（模型卸载重载的开销）
- → 全库 3445 片重建约 **28 分钟**。**这是硬件限制，不是 bug**，我一度以为卡死了。

- **向量维度：1024（bge-m3）**
- 存储方式：`json.dumps(list[float])` 存进 SQLite TEXT 列

### 5.5 检索链路与"按库 Top-K"（设计亮点）

```python
def search(user_id, query, top_k=None, collection_ids=None):
    # ① 一次查库：user_id + collection_ids 双重过滤
    rows = db.query(KbChunk).filter(KbChunk.user_id == user_id)
    if collection_ids:
        rows = rows.filter(KbChunk.collection_id.in_(collection_ids))

    # ② query 向量化（只有这一步是网络请求，也是真正的瓶颈）
    qvec = embed_texts([q])[0]

    # ③ 内存里按 collection_id 分组打分（余弦相似度）
    for r in rows:
        vec = json.loads(r.embedding)
        groups[r.collection_id].append((r.text, r.file_id, _cosine(qvec, vec)))

    # ④ 每个库各取自己的前 K 名 ← 关键设计
    for cid, items in groups.items():
        k = per_collection.get(cid) or config.RAG_TOP_K
        items.sort(key=lambda x: x[2], reverse=True)
        merged.extend(items[:k])

    # ⑤ 合并排序 + 总上限保护
    merged.sort(key=lambda x: x[2], reverse=True)
    return merged[: config.RAG_MAX_TOTAL_CHUNKS]   # 默认 30
```

**为什么 Top-K 要"按库生效"而不是全局取 N 条？**

> 因为**不同库的用途不同**：
> - 规范/教材类库需要**精确定位** → Top-K 设小（如 2~3）
> - 杂项资料库需要**多召回** → Top-K 设大（如 8~10）
>
> 如果全局取 N 条，大库会把小库的结果全挤掉。
> 我的实现是**每个库各取自己配置的条数，再合并按相似度排序**，两种需求可以并存。
>
> 数据模型上：`kb_collections.top_k` 可为每个库单独设置，
> **NULL = 跟随全局 `RAG_TOP_K`（默认 4）**。

**余弦相似度实现**：

```python
def _cosine(a, b) -> float:
    if not a or not b or len(a) != len(b): return -1.0   # 维度不一致视为不相似
    dot = sum(x*y for x, y in zip(a, b))
    na = math.sqrt(sum(x*x for x in a))
    nb = math.sqrt(sum(y*y for y in b))
    if na == 0 or nb == 0: return -1.0                   # 零向量保护
    return dot / (na * nb)
```

> 面试可补充：**bge-m3 输出的向量本身接近归一化**，此时余弦 ≈ 点积，
> 理论上可省掉两次开方。我保留了完整余弦是为了**换 embedding 模型时不出错**。

**RAG 参数一览**（都在 `.env` 可调）：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `RAG_CHUNK_SIZE` | 500 | 每片段目标字符数 |
| `RAG_CHUNK_OVERLAP` | 80 | 相邻片段重叠字符数 |
| `RAG_TOP_K` | 4 | 全局默认检索片段数 |
| `RAG_MAX_TOTAL_CHUNKS` | 30 | 多库合并后的总上限（防撑爆上下文） |
| `RAG_EMBED_BATCH` | 32 | 向量化批大小 |
| `EMBED_MODEL` | bge-m3 | 向量模型（1024 维） |

### 5.6 检索结果如何进模型

知识库检索是**一个工具**，不是硬编码的前置步骤：

```python
@tool
def search_knowledge_base(query: str) -> str:
    """在用户上传的知识库文档中检索最相关的片段。当用户询问其上传资料
    （课程笔记、报告、说明书、规范、合同等）里的具体内容时使用。
    输入检索问题，返回若干相关片段并标注来源文件名。"""
    hits = search(user_id, query, collection_ids=kb_ids)
    # file_id → 文件名映射
    blocks = [f"【{names.get(fid)}】{text}" for text, fid, _ in hits]
    return "\n\n".join(blocks)
```

**为什么做成工具而不是每次都检索？**（高频追问）

> 因为**不是每个问题都需要查知识库**。问"今天北京天气"去检索知识库是浪费，
> 还会污染上下文。做成工具后，**模型自己判断要不要查、用什么关键词查**——
> 它甚至可以为了一个问题查多次（换不同关键词）。
>
> 代价是多一轮模型往返。权衡下来我认为值得：**准确性 > 一点点延迟**。

**来源标注的实现**：工具返回文本用 `【文件名】正文` 格式，
流式链路里捕获 `ToolMessage(name="search_knowledge_base")`，
用正则 `【(.+?)】` 提取文件名，推 `{"sources": [...]}` 事件给前端做引用标注。

### 5.7 知识库不分库（架构决策，被问过很多次）

**所有片段存一张 `kb_chunks` 表**，靠 `user_id + collection_id` 双重过滤隔离。

> **不要给每个知识库建一张表**——这会让跨库检索、按库 Top-K、删库全部复杂化。
> 单表 + 双重过滤在语义上等价于分库，而且这正是
> **Chroma 的 collection / Milvus 的 partition 的标准思路**。

## 六、流式输出（SSE）实现

### 6.1 为什么用 SSE 而不是 WebSocket

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端 → 客户端） | 双向 |
| 协议 | 纯 HTTP | 需升级协议 |
| 断线重连 | 浏览器原生支持 | 需自己实现 |
| 代理/网关兼容 | 好 | 部分环境需额外配置 |
| 实现复杂度 | 低 | 高 |

> **AI 打字机场景是纯单向推送**，SSE 完全够用，而且更简单、更易过代理。
> 我的实现就是一个 Python 生成器 + `StreamingResponse`：

```python
return StreamingResponse(
    gen(),
    media_type="text/event-stream",
    headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
)
```

> `X-Accel-Buffering: no` 是给 Nginx 看的——**关掉缓冲，否则 token 会被攒着一起发**，
> 打字机效果就没了。

### 6.2 事件协议设计（5 种事件）

| 事件 | 载荷 | 用途 |
|---|---|---|
| `{"token": "..."}` | 正文增量 | 打字机主体 |
| `{"reasoning": "..."}` | 思考过程增量 | 推理模型的思维链，前端单独折叠展示 |
| `{"sources": [...]}` | 来源文件名 | RAG 命中来源标注 |
| `{"error": "..."}` | 结构化错误原因 | 前端弹真实原因而非静默失败 |
| `{"done": true, provider, model, user_id, assistant_id}` | 结束 | 回传本轮用的模型 + 两行消息 id |

> `done` 事件为什么要带 `user_id` / `assistant_id`？
> 因为**新发的消息在前端还没有后端 id**，不带回来的话，
> "单条删除"按钮就不会显示，必须刷新页面才能删。

### 6.3 思考内容剥离（`_ThinkSplitter`，细节控加分项）

**问题**：本地 qwen3 开启 think 时，思考过程会用
` thinking ... <｜end▁of▁thinking｜>` 标签**混在正文里**。直接推给前端，
用户会看到一大段乱码般的标签。

**难点**：**标签可能跨 chunk**——一个 chunk 结尾是 `<｜end▁of`，下一个 chunk 才是 `thinking｜>`。

**解法**：状态机 + 尾巴缓冲

```python
class _ThinkSplitter:
    def feed(self, text: str) -> tuple[str, str]:   # 返回 (思考增量, 回答增量)
        self._buf += text
        while self._buf:
            if not self._in_think:
                i = self._buf.find(_THINK_OPEN)
                if i >= 0: ...切换状态...
                # 末尾可能是半个开标签 → 留住 len(tag)-1 个字符不输出
                keep = len(_THINK_OPEN) - 1
                if len(self._buf) > keep:
                    answer_parts.append(self._buf[:-keep])
                    self._buf = self._buf[-keep:]
                break
            ...
```

**关键在 `keep = len(tag) - 1`**：保留可能是"半个标签"的尾巴，
既不会把半个标签当正文吐出去，也不会漏字。流结束时调 `flush()` 冲掉残留。

云端推理模型（DeepSeek-R1 / Qwen 思考版）走的是另一条路：
`msg.additional_kwargs["reasoning_content"]`，**结构化字段，不用剥离**。

### 6.4 断连兜底（健壮性设计，最容易被夸）

**问题**：用户中途关窗口或点"停止"，会发生什么？

**我的设计**：

```python
# ① 不在流结束时才建消息行，而是【一开始就建一条空内容行】
row = Message(conversation_id=conv.id, role="assistant", content="", ...)
sdb.add(row); sdb.commit(); sdb.refresh(row)
assistant_id = row.id

# ② 流过程中只在 finally / except 里更新它
except GeneratorExit:
    partial = "".join(full)
    reply = partial if partial.strip() else "（回答生成已中断）"
    _save(reply)                  # 行早已存在，只写回部分内容
    _clear_session_memory(conv.id)  # 清掉可能的半截工具调用历史
    raise                          # 必须 re-raise，符合生成器关闭协议
```

**三个要点**：

1. **预建空行**：即便客户端断连，这条行已存在，用户重载会话能看到"回答中断"状态，
   而不是**一条凭空消失的回答**。
2. **`GeneratorExit` 里必须 `raise`**：否则 Python 会报
   `RuntimeError: generator ignored GeneratorExit`。落库要放在 `raise` **之前**。
3. **断连后清会话记忆**：中断可能发生在"工具调用进行到一半"，
   checkpointer 会残留半截历史，导致该会话之后每次请求都报错（见 7.5）。

> 补充细节：Starlette **未必会立刻对 sync 生成器抛 GeneratorExit**，
> 所以我用独立的 `SessionLocal()` 做落库（不复用请求级 db session，避免被提前回收）。

### 6.5 错误不静默

```python
except Exception as e:
    traceback.print_exc()          # ① 后端控制台打完整堆栈
    err_text = str(e) or e.__class__.__name__
    body = getattr(e, "body", None)  # ② 抽平台的详细错误
    if isinstance(body, dict):
        detail = body.get("message") or body.get("error")
        if detail: err_text = f"{err_text}｜{detail}"
    reply = f"出错了: {err_text}"
    _save(reply)
    _clear_session_memory(conv.id)
    yield f"data: {json.dumps({'error': err_text})}\n\n"   # ③ 前端拿结构化原因
```

> 之前云端报错（401 / 429 / 参数不合法 / 超时）被静默吞成一行"出错了"，
> 用户完全不知道为什么。**我的原则是：出错别静默吞——后端打印堆栈，前端展示真实原因**，
> 让用户能自助排查。

## 七、遇到的 10 个真实问题与解决方案

> 这一节是答辩的**主战场**。每个问题都按「现象 → 排查 → 根因 → 解决 → 量化结果」讲。

### 7.1 ⭐ 首字延迟 42 秒 → 1 秒（最硬核的一个，务必讲透）

**现象**：每次提问要等 30~60 秒才出第一个字，还频繁报 `ConnectTimeout`。用户感知是"又慢又报错"。

**排查方法论**（这个比结论更值钱）：
> 我坚持**先量化再改代码**。写了一次性探测脚本测「首字/握手耗时」，
> 分层对比：**裸模型 → bind_tools → agent.stream**。
> 这样能迅速区分瓶颈在模型、prompt、langgraph 还是网络。
>
> **关键判据**：冷启动 vs 热请求差异巨大 → **一定是连接/握手问题，不是模型问题**。
> 实测：热请求 0.9s，冷建连 23s+。差了 25 倍，模型不可能有这么大波动。

**根因有两个，叠加在一起**：

**根因① 连接池保活太短**
> httpx 默认 `keepalive_expiry=5s`，空闲即断。
> 而用户"打字 → 发送"的间隔通常 **>5 秒**，
> 于是**每次提问都在重新握手**（走代理重建 TLS 要 20~40s）。
> 这解释了"时快时慢"——快速连发就快，隔一会儿再问就慢。

**根因② langchain-openai 破坏了代理自动探测**
> 这个坑非常隐蔽：langchain-openai 会为 `http_socket_options`
> **注入自定义 httpx transport**，而该行为会**禁用 httpx 的代理自动探测**
> （它的 stderr 里有明确警告，但很容易被忽略）。
> 所以我一开始改 `http_client(trust_env=True)` **完全没用**。
>
> 而本机（及多数国内网络）**必须经代理**才能和云端平台建立 TLS，
> 强制直连就反复握手超时。

**解决**：

```python
# 模块级【全局共享】client（不是每次新建）
_CLOUD_HTTP = httpx.Client(
    proxy=proxy,               # ← 显式传，不依赖自动探测
    trust_env=False,           # ← 已显式决定，行为可预期
    timeout=httpx.Timeout(180.0, connect=30.0),
    limits=httpx.Limits(
        max_keepalive_connections=16,
        max_connections=32,
        keepalive_expiry=600.0,   # ← 5s → 600s，关键中的关键
    ),
)

# 传给 ChatOpenAI
kwargs["http_client"] = _cloud_http_client()
kwargs["http_socket_options"] = ()   # ← 阻止 langchain-openai 注入自定义 transport
```

**四个必须注意的点**（说出来就是深度）：
1. **`openai_proxy` 与 `http_client` 互斥**，同时传会 pydantic 报错。
2. **不用 `openai_proxy`** 的原因：它每次新建 client，**无法复用连接池**——治标不治本。
3. **`http_socket_options=()`** 是阻止 langchain 破坏代理配置的关键。
4. **代理地址变化时自动重建 client**（比对 `_CLOUD_PROXY_USED`），无需重启后端。

**结果**：首字延迟 **42s → 1~3s**，`ConnectTimeout` 消失。

### 7.2 代理端口会变，导致"自动检测"失效

**现象**：明明配了代理，还是慢。查发现环境变量里的代理端口已经不存在了。

**根因**：
> 代理软件（本机实测端口从 `53953` → `57563` → `65262` 变过三次）**会随机取高端口**。
> 而环境变量是**进程启动时继承**的，代理软件改端口后不会更新。
> 后端起进程时抓到的地址可能**已经失效**。

**解决：四级优先级 + 启动时自动扫描自愈**

```python
def cloud_proxy_url() -> str | None:
    if config.CLOUD_TRUST_ENV: return None       # ① 用户明确要求直连
    if config.CLOUD_PROXY_URL: return config.CLOUD_PROXY_URL   # ② 显式配置最高
    if _AUTO_PROXY: return _AUTO_PROXY            # ③ 自动检测结果
    return os.environ.get("HTTPS_PROXY") or ...   # ④ 环境变量兜底
```

**自动扫描的实现**（`_auto_find_proxy`）：
1. 用 `netstat -ano -p tcp` 列出本机所有 LISTENING 端口（仅回环/通配地址）
2. 对每个端口发一个 **HTTP CONNECT 探测**，看它能不能连到云端平台
3. 能连的就是代理

```python
def _is_http_proxy(port, host, tport, timeout=1.0) -> bool:
    with socket.create_connection(("127.0.0.1", port), timeout=timeout) as s:
        s.sendall(f"CONNECT {host}:{tport} HTTP/1.1\r\n...".encode())
        resp = s.recv(64).decode(errors="ignore")
    return resp.startswith("HTTP/1.0 200") or resp.startswith("HTTP/1.1 200")
```

> **性能设计**：未监听的端口会**立即 RST**（不等超时），监听但非代理的端口最多等 1s。
> 所以全端口扫描很快，且**只在预热失败时才触发**，不影响正常路径。

**⚠️ 一个具体的坑（说出来很真实）**：
> 我的端口扫描上限最初写成 `65000`，结果**扫不到代理**——
> 因为代理端口可能 **> 65000**（实测到过 `65262`）。
> 上限必须是 **`<= 65535`**。而且这个错我在 `agent_manager` 和 `llm_config`
> **两处都犯了**，改的时候两处都要对。

**触发时机**：`warm_up_cloud()` 预热失败时自动扫描并重建 client，
用户完全无感知。启动时预热一次 + 每 60s 后台保活一次。

### 7.3 后端重启后 AI"失忆"，但界面历史还在

**现象**：昨晚聊过的内容，今早问 AI 却说"我看不到之前的对话记录"。
但界面上明明还显示着那些消息。

**根因**：**两套存储不一致**
- 界面历史 ← `messages` 表（SQLite，**持久**）
- AI 上下文 ← `MemorySaver`（**纯内存，进程退出即失**）

**解决**：换成 `SqliteSaver`，记忆写进 `data/checkpoints.db`。
配合全局共享 checkpointer + `thread_id` 隔离（见 4.6）。

> **反思**：这个 bug 的本质是**同一份"对话历史"有两个真相源**。
> 现在依然是两套（messages 表给前端看、checkpoints 给模型看），
> 但至少都持久化了。理想方案是让模型上下文**从 messages 表按需重建**，
> 只保留一个真相源——这是我在演进路线里列的一项。

### 7.4 `database is locked` —— 重建索引时整个服务挂掉

**现象**：批量重建知识库索引时，其他所有请求都报 `database is locked`，
连 `init_db()` 都跑不过。

**根因**：SQLite 默认 `journal_mode=DELETE`，**写会阻塞读**。
长时间批量写（几千个片段）期间，整个库对外不可用。

**解决**：开 WAL + 配套调优

```python
@event.listens_for(engine, "connect")
def _sqlite_pragmas(dbapi_conn, _record):
    cur = dbapi_conn.cursor()
    cur.execute("PRAGMA journal_mode=WAL")      # 读写可并发
    cur.execute("PRAGMA synchronous=NORMAL")     # WAL 下的推荐搭配
    cur.execute("PRAGMA busy_timeout=30000")     # 撞锁等 30s 而非立刻抛错
```
加上 `connect_args={"check_same_thread": False, "timeout": 30}`。

**⚠️ WAL 的副作用（这个坑很阴，讲出来特别有说服力）**：
> **外部工具可能读到"旧数据"**。
> 写入先进 `app.db-wal`，未 checkpoint 前**不落主 `app.db`**。
> 只读主文件、不读 `-wal` 的工具（某些简易 SQLite 查看器）会看到**修改前的快照**。
>
> 我一度以为"数据没改成功"，其实是这个原因。
>
> **排查方法**：对比两种连接方式的结果
> ```python
> connect("file:app.db?mode=ro&immutable=1")   # 只读主文件（会看到旧数据）
> connect("app.db")                            # 正常连接（自动合并 WAL）
> ```
> 结果不一致 → 就是 WAL 未合并，**不是数据没改**。
>
> **解决**：`PRAGMA wal_checkpoint(TRUNCATE)`。
> DB Browser / DBeaver 能正确处理 WAL，不用担心。

> **方法论沉淀**：排查"数据不见了 / 没删掉"时，**先确认读取视角**
> （WAL / 缓存 / user_id 归属），再怀疑数据本身。

### 7.5 会话彻底坏掉：`Found AIMessages with tool_calls that do not have a corresponding ToolMessage`

**现象**：某个会话之后**每次提问都报这个错**，换成本地模型也一样失败。

**根因**：
> 网络异常或用户中断时，如果**恰好在"工具调用进行到一半"**终止，
> checkpointer 会残留一条「AIMessage 带 `tool_calls`、却没有对应 `ToolMessage`」的**半截历史**。
>
> **关键**：这个错误发生在 LangGraph 的**历史校验阶段**，即「调用模型之前」——
> 所以**换模型完全没用**，只能清掉该会话的记忆。

**解决**：在 `except GeneratorExit` 和 `except Exception` 里都调
`_clear_session_memory(conv_id)` → `_CHECKPOINTER.delete_thread(str(conv_id))`。

**影响可控**：
> 前端消息记录（`messages` 表）**不受影响**，历史照样看得到；
> 只是 AI 的上下文记忆被重置（相当于这个会话"失忆"，但能继续用）。
> 这比"会话彻底废掉"好得多。

### 7.6 分片碎片化：322/3100 片段以逗号开头

**现象**：检索出来的片段经常是半句话，以逗号或引号开头，语义不完整。

**排查**：我写了个统计脚本扫描全部片段的开头字符，
**实测 3100 片里有 322 片（约 10%）以逗号/引号开头**。

**根因**：定长窗口切分 + overlap 回退不校正边界（见 5.2）。

**解决**：重写为**语义感知三段式切分**（拆单元 → 贪心合并 → 回退完整单元做重叠）。

**⚠️ 统计口径也踩过坑**：
> 我最初把"以分号/冒号收尾"也算作"片段未完结"，结果**误报率高达 41%**。
> 但实际上**分号/冒号收尾在条目式文本（校规、法条、规范）里是完全合法的边界**。
> 修正口径后才是真实数字。
>
> **教训**：定指标之前先想清楚"什么才算问题"，否则会追着假问题跑。

### 7.7 大文件上传卡死整个服务

**现象**：上传一个几十 MB 的 PDF，上传期间**所有其他请求都没响应**。

**根因**：解析 PDF 和建索引是 **CPU 密集 + 长时间**操作，
直接写在 `async def` 里会**阻塞事件循环**——FastAPI 的异步是单线程事件循环，
一个慢操作就把所有请求都堵住了。

**解决**：`run_in_threadpool` 把重活扔进线程池

```python
content = await run_in_threadpool(_extract_text, data, ext)
...
await run_in_threadpool(index_file, current_user.id, item.id, content, collection_id)
```

**配套细节**：
- **先按 `file.size` 预判超限再读盘**，避免把大文件整个读进内存才发现超限
- **索引失败不影响上传本身**（try/except pass）——文件先存住，可以之后手动 reindex
- 提供 `POST /api/files/{id}/reindex` 单独重建

### 7.8 倒计时不响铃（浏览器 AudioContext 策略）

**现象**：计时器到点了，**完全没有声音**，但界面提示正常。

**根因（两条叠加）**：
1. **浏览器的自动播放策略**：网页要出声，`AudioContext` 必须在**用户手势（点击）的那一刻**创建或激活。而倒计时结束是**定时器回调**（不算用户操作），这时才新建的音频上下文会被浏览器**拒绝发声** → 静音。
2. 到点后紧跟一个 `alert()`，它**卡住主线程**，把铃声推到弹窗关闭之后才响。

**解决**：
- 改成**全局复用同一个 AudioContext**（`chime.ts`，不再每次新建）
- 新增 `unlockAudio()`：在用户点「开始」时就把音频解锁 ← **关键一步**
- 到点后**去掉阻塞式 alert**（视觉提示改由按钮变「已结束」+ 站内通知承担）

> **通用结论**：任何"延迟触发的声音"都必须**在用户交互时预先解锁音频上下文**。
> 这是 Web 前端的通病，不是我的代码逻辑错。

### 7.9 `python-dotenv` 不支持行内注释（配置类 bug 最难查）

**现象**：`cloud_configured` 显示已配置但实际调不通；旧模型名像僵尸一样冒出来。

**根因**：
> ```
> CLOUD_MODEL=   # 这是说明
> ```
> python-dotenv 会把 **`# 这是说明` 整个当成值**！它不支持行内注释。

**解决**：
1. **注释必须独占一行**（写进了项目约定）
2. 代码里加兜底 `_clean_env()`：**值以 `#` 开头就视为空**

> **教训**：配置解析这类"看起来不可能出错"的地方，往往藏着最难的 bug。
> 因为它不报错，只是**静默地给你一个错误的值**。

### 7.10 增量迁移：`create_all` 不会给已有表加列

**现象**：新加了个字段，本地新库正常，**老库直接报 no such column**。

**根因**：SQLAlchemy 的 `Base.metadata.create_all()` **只建缺失的表，不会修改已存在的表**。

**解决**：`init_db()` 里写增量迁移

```python
inspector = _sa_inspect(engine)
existing = {c["name"] for c in inspector.get_columns("conversations")}
with engine.begin() as conn:
    if "provider_id" not in existing:
        conn.execute(text("ALTER TABLE conversations ADD COLUMN provider_id INTEGER"))
```

还包含**老数据回填**（给无归属的文件补默认知识库）和
**历史数据修复**（早期原生 SQL 插入的记录 `created_at` 为空）。

> **诚实说明**：这是**开发期的权宜方案**。生产环境应该用 **Alembic** 做版本化迁移——
> 手写 ALTER 无法回滚、无版本记录、多分支合并会冲突。
> 我在演进路线里列了这一项。（主动说出短板比被问出来好）

### 8.4 RAG 与向量检索（重点）

| # | 问题 | 答题要点 |
|---|---|---|
| 32 | 讲讲你的 RAG 全链路 | 见 5.1（入库）+ 5.5（检索），能完整说出来 |
| 33 | 为什么不用向量数据库？ | **数据规模决定**：3445 片属 0~5 万档，SQLite + 纯 Python 余弦足够（毫秒级）。且**真正瓶颈是 embedding 的网络往返，换库省不掉**。架构上已隔离，换库只改两个函数 |
| 34 | 什么时候该换？ | 5 万~50 万片上 SQLite+FAISS；50 万+ 或多租户水平扩展才上 Chroma/Milvus |
| 35 | chunk size 为什么定 500？ | 经验值：太小（<200）语义不完整、检索碎片化；太大（>1000）会稀释相关性且吃上下文。**500 字符约等于一个自然段落** |
| 36 | overlap 为什么要重叠？ | 防止关键信息恰好落在切分边界被劈开。**我的重叠是"回退若干完整单元"而非固定 80 字符**，所以重叠区也是完整句子 |
| 37 | 你的切分和定长切分有什么区别？ | 定长切分实测 **322/3100 片以逗号开头**。我改成语义感知三段式：拆最小语义单元 → 贪心合并 → 回退完整单元做重叠 |
| 38 | 怎么切分中英文混排？ | 句末符只取 `。！？!?；;`；**`…` 和 `——` 绝不能当句末符**（中文里多是句中停顿，实测会产生以 `…` 开头的碎片） |
| 39 | 余弦相似度和欧氏距离有什么区别？为什么用余弦？ | 余弦看**方向**（语义相似度），不受向量长度影响；欧氏看**绝对位置**。文本语义检索的标准选择是余弦。bge-m3 向量接近归一化，此时余弦≈点积 |
| 40 | Top-K 取多少？怎么定的？ | 全局默认 4，**但支持按库单独设置**（规范库要精准设小，资料库要广撒网设大）。多库检索时**每库各取自己的 K，再合并排序**，最后有 30 的总上限保护 |
| 41 | 检索准确率怎么评估的？ | 诚实答：**没有建立量化评估集**（没有 recall@k / MRR）。目前是人工抽查片段完整性。**这是最大的短板**，应该建 golden set |
| 42 | 怎么提升检索质量？（高频） | **混合检索（向量 + BM25 关键词）**——对"路明非""校政〔2017〕97号"这类专有名词提升明显，只改 `rag.py`。进阶：Rerank（bge-reranker）、Query 改写、HyDE、父子chunk |
| 43 | 向量维度多少？为什么？ | **1024 维（bge-m3）**。bge-m3 支持稠密+稀疏+多向量，中文效果好，本地可跑零 API 成本 |
| 44 | 3445 个 1024 维向量占多少空间？ | 约 `3445 × 1024 × 4B ≈ 14MB`（float32）。但我存的是 JSON 文本，**膨胀到约 48MB**（每字符约 1 字节 + 分隔符）。这是 JSON 存储的代价，换二进制能省 3 倍 |
| 45 | 文档更新了怎么办？ | `index_file()` **先删该文件旧片段再写新的**，所以幂等可重复执行。另有 `POST /api/files/{id}/reindex` 手动重建 |
| 46 | 改了切分算法，存量索引怎么办？ | **不会自动更新**，需重建。我提供了单文件 reindex 接口 + 批量遍历 files 表调 `rag.index_file()` |
| 47 | 扫描版 PDF 怎么办？ | 抽不到文字，需 OCR。**目前是明确提示用户**（返回"可能是扫描件，可先 OCR"），没做 OCR |
| 48 | 上传时的解析为什么放线程池？ | CPU 密集 + 耗时长，直接写在 async 里会**阻塞事件循环**，导致所有请求无响应 |
| 49 | 向量化为什么要分批？ | 长文档上千片段一次性 POST 必超时（120s 也扛不住）。批大小 32，实测**批量 21s / 单条 15s**（模型卸载重载），全库重建约 28 分钟 |
| 50 | 知识库为什么不分表？ | 单表 + `user_id`/`collection_id` 双重过滤等价于分库，且这是 Chroma collection / Milvus partition 的标准思路。分表会让跨库检索、按库 Top-K、删库全部复杂化 |

## 九、已知短板与演进路线

> **主动说短板是加分项**。面试官问"你觉得项目有什么不足"时，照这个讲。

### 9.1 当前短板（诚实清单）

| 短板 | 影响 | 优先级 |
|---|---|---|
| **无单元测试覆盖** | 重构没安全网，切分算法这类纯函数最该测 | 🔴 高 |
| **RAG 无量化评估** | 说不上"检索准确率多少"，只能人工抽查 | 🔴 高 |
| **Agent 缓存无 LRU 上限** | 长期运行可能内存增长 | 🟡 中 |
| **API Key 数据库明文存储** | 数据库泄露即密钥泄露 | 🟡 中 |
| **无 refresh token** | JWT 过期需重新登录 | 🟡 中 |
| **无接口限流** | 可能被刷爆 API 配额 | 🟡 中 |
| **手写 ALTER 迁移** | 无法回滚、无版本记录 | 🟡 中 |
| **未设 recursion_limit** | 理论上模型可能反复调工具 | 🟢 低 |
| **无 Docker 化** | 环境一致性问题（我踩过 orjson DLL 被 SAC 拦截） | 🟢 低 |
| **向量 JSON 存储膨胀 3 倍** | 48MB vs 理论 14MB | 🟢 低 |
| **无 Prompt 注入防护** | 知识库内容拼进上下文有风险 | 🟢 低 |

### 9.2 演进路线（按性价比排序）

**第一梯队（改动小、收益大）**
1. **混合检索（向量 + BM25）**：只改 `rag.py`，对专有名词（人名、文号）提升明显
2. **给 `split_text` / `_cosine` / 工具函数补单测**：纯函数最好测，投入产出比最高
3. **建 RAG 评估集**：50~100 条 QA 对，算 recall@k / MRR，让"质量"可量化
4. **Agent 缓存加 LRU**（`functools.lru_cache` 或手写 OrderedDict，上限如 200）

**第二梯队（架构级）**
5. **Rerank**：检索 Top-20 → bge-reranker 精排 Top-4，准确率提升明显
6. **上下文管理**：目前**历史无限增长**（没有截断），长会话会撑爆上下文。应加滑动窗口 + 摘要压缩
7. **API Key 加密**：Fernet 对称加密，密钥放系统 keyring
8. **Alembic 迁移**：替换手写 ALTER
9. **Docker 化**：docker-compose 一键起前后端 + Ollama

**第三梯队（规模化）**
10. **向量库迁移**：数据量到 5 万片时上 FAISS / Chroma
11. **PostgreSQL**：并发上量后替换 SQLite
12. **消息队列**：索引构建改异步任务（Celery/RQ），上传立即返回、后台建索引
13. **可观测性**：接入 Prometheus + 结构化日志，量化首字延迟/工具调用成功率

## 附：答辩现场的三条建议
